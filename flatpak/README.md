# Flatpak packaging for Jotta Desktop

## Strategy

Jotta Desktop is a **thin frontend** for Jottacloud's official `jottad`/`jotta-cli`
daemon. The Flatpak bundles only our own Rust code (`jotta-desktop` + `jotta-tray`).
The user must have `jotta-cli` and `jottad` installed on the host (via Jottacloud's
official installer, COPR, AUR, etc.). The app finds them via `PATH`.

**Why not bundle jotta-cli?** Jottacloud's binaries are proprietary. Bundling them
in a Flatpak requires written redistribution permission (Flathub policy). Until
permission is obtained, the app expects host-installed binaries.

## Files

| File | Purpose |
|------|---------|
| `io.github.eske.JottaDesktop.json` | Flatpak manifest |
| `io.github.eske.JottaDesktop.service` | D-Bus activation service (required because the desktop file has `DBusActivatable=true`) |
| `cargo-sources.json` | Vendored crate sources (262 entries: 131 archives + 131 checksum files) |

## Export rules (why icon names matter at runtime)

flatpak-builder only exports files under `share/applications`, `share/icons`,
`share/metainfo`, `share/dbus-1/services` whose **filename starts with the
app-id** — everything else is skipped ("non-allowed export filename"). Therefore:

- The tray and GUI reference icons by the app-id names
  (`io.github.eske.JottaDesktop-*`). The `jotta-desktop*` copies are still
  shipped in the repo for native installs, where both names resolve.
- The tray also embeds ARGB32 pixmaps (`pixmaps.rs`), so the icon is visible
  even if the theme lookup fails.
- `DBusActivatable=true` in the desktop file requires
  `/app/share/dbus-1/services/io.github.eske.JottaDesktop.service`
  (with `Exec=/app/bin/jotta-desktop`) — otherwise the export fails with
  "Desktop file D-Bus activatable, but service file not exported".

## How cargo-sources.json works

`cargo-sources.json` is a flatpak-builder sources file (same format as generated by
`flatpak-cargo-generator.py`). It contains:

- **131 `"type": "archive"` entries** — each downloads a `.crate` file from
  `static.crates.io` and extracts it to `cargo/vendor/<name>-<version>/`
- **131 `"type": "inline"` entries** — each creates a `.cargo-checksum.json` file
  inside the extracted crate directory (required by cargo's vendor format)

flatpak-builder downloads and extracts all sources **before** running `build-commands`,
so the build sandbox never needs network access. The `.cargo/config.toml` then points
cargo at the vendored directory.

This is the standard Flathub approach for Rust apps.

## Building

### 1. Install prerequisites

```bash
# Install flatpak-builder
sudo dnf install flatpak-builder

# Install the GNOME 50 SDK + Platform + Rust extension
flatpak install flathub org.gnome.Sdk//50 org.gnome.Platform//50
flatpak install flathub org.freedesktop.Sdk.Extension.rust-stable//25.08
```

> **Note on versions**: GNOME 48 is EOL (since March 2026). We target GNOME 50
> which is based on Freedesktop SDK 25.08. The Rust extension branch must match
> the Freedesktop SDK version — for GNOME 50, use `rust-stable//25.08`.

### 2. Build and install

```bash
flatpak-builder --user --install --force-clean build-dir flatpak/io.github.eske.JottaDesktop.json
```

### 3. Run

```bash
flatpak run io.github.eske.JottaDesktop
```

## Regenerating cargo-sources.json

When dependencies change (after `cargo update`):

```bash
# Option 1: Use flatpak-cargo-generator (recommended)

flatpak-cargo-generator Cargo.lock -o flatpak/cargo-sources.json

# Option 2: Use the manual script in scripts/
python3 scripts/generate-cargo-sources.py
```

## Prerequisites on the host

The user needs `jotta-cli` and `jottad` installed (RPM/DEB packages put them in
`/usr/bin`, the tarball installer in `~/.jottacloud/bin`):

```bash
# Fedora/RHEL (official RPM repo)
sudo dnf copr enable ...   # or the official repo from docs.jottacloud.com
# or the tarball installer:
curl -s https://repo.jotta.cloud/install.sh | bash
```

## How host binaries are found and executed

Inside the sandbox, `PATH` is only `/app/bin:/usr/bin` (the runtime's), so the
app cannot see host binaries on `PATH`. `BinaryLocator::from_path()` therefore
also searches (first existing file wins):

1. `$JOTTA_CLI` / `$JOTTAD` env overrides
2. `PATH`
3. next to our own executable
4. `~/.jottacloud/bin` (tarball installer)
5. `/run/host/usr/local/bin`, `/run/host/usr/bin` (host OS via `--filesystem=host-os`; RPM/DEB install to `/usr/bin` on the host)
6. `/usr/local/bin`, `/usr/bin` (native)

When a **host** binary is found while running in a Flatpak (`/.flatpak-info`),
it is executed **on the host** via `flatpak-spawn --host -- <host path>`
(`host_spawn_prefix()` in `cli.rs`). This needs the
`--talk-name=org.freedesktop.Flatpak` finish-arg and gives jotta-cli the host's
PATH, `~/.config/jottacloud` and the jottad socket — exactly like a terminal.
`DaemonSupervisor::ensure_running()` likewise starts jottad detached on the host
(`nohup ... &`), because a daemon spawned inside the sandbox would die with the
sandbox. If the host already runs jottad (systemd user unit `jottad.service`),
the socket at `$XDG_RUNTIME_DIR/jottad/jottad.socket` is reused and nothing is
spawned.

## Finish-args explained

| Arg | Why |
|-----|-----|
| `--share=network` | jotta-cli talks to Jottacloud API + jottad socket |
| `--share=ipc` | D-Bus for StatusNotifierItem tray |
| `--socket=fallback-x11` / `--socket=wayland` | GUI display |
| `--socket=session-bus` | Session D-Bus (notifications, SNI) |
| `--filesystem=host` | Read/write backup source folders anywhere on the host |
| `--filesystem=host-os` | See host `/usr/bin` etc. at `/run/host/...` (find host jotta-cli/jottad) |
| `--filesystem=xdg-run/jottad` | Access jottad's Unix socket |
| `--talk-name=org.freedesktop.Flatpak` | `flatpak-spawn --host`: run jotta-cli/jottad on the host |
| `--filesystem=xdg-config/autostart:ro` | Read autostart entries (launch-on-startup toggle) |
| `--talk-name=org.freedesktop.Notifications` | Desktop notifications |
| `--talk-name=org.kde.StatusNotifierWatcher` | KDE tray icon support |

## AppStream / appstreamcli compose requirements

`flatpak-builder` runs `appstreamcli compose` after the build. It fails the build
on errors such as `icon-not-found` and `filters-but-no-output`. Three rules matter:

1. **Icons must be named after the app-id** (`io.github.eske.JottaDesktop.*`),
   not the executable name. We therefore ship every icon twice in
   `data/icons/hicolor/`: as `jotta-desktop*.png/svg` (used by the tray at
   runtime) and as `io.github.eske.JottaDesktop*.png/svg` (used by
   appstreamcli/Flathub). Sizes: 16–256 px PNG + 512x512 PNG + scalable SVG +
   symbolic.
2. **The desktop file must be installed as `<app-id>.desktop`**
   (`/app/share/applications/io.github.eske.JottaDesktop.desktop`) and the
   metainfo `<launchable>` must point to that name. flatpak-builder only
   accepts components `io.github.eske.JottaDesktop` and
   `io.github.eske.JottaDesktop.desktop`; anything else is filtered out
   (`filters-but-no-output`). The desktop file's `Icon=` is set to the app-id.
3. **`mkdir -p /app/share/icons` before `cp -r data/icons/hicolor /app/share/icons/`**.
   If `/app/share/icons` does not exist yet, `cp -r` creates it as a copy of
   `hicolor` itself, so icons land in `/app/share/icons/16x16/...` instead of
   `/app/share/icons/hicolor/16x16/...` and appstreamcli finds nothing.
